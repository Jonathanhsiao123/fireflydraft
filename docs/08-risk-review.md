# 08 · 原藍圖漏洞審查與修訂方案

> 狀態：完成。本文件逐條列出原《專案主藍圖》中的技術、臨床、合規與事實性問題，並給出修訂方案。修訂已反映於 README 與各分冊 TODO。

## A. 架構與工程問題

### A1. 「即時」定義自相矛盾 (嚴重)
- 問題：藍圖 5.1 節聲稱「Fable 5 會實時分析傳回的視線向量數據」並在 3 秒 RJA 時間窗內判定成敗，但 2.3 與 6.1 節又將 Fable 5 定位為非同步批次引擎。雲端前沿模型的往返延遲 (數秒至數十秒) 與計費模式，物理上不可能承擔 60Hz 眼動流的秒級判定。
- 修訂：制定硬性規則「任何 < 5 秒 SLA 的決策不得依賴任何雲端 LLM」。RJA 成敗判定、提示升級、代幣發放全部改為邊緣端確定性幾何規則 (視線向量與目標 bounding volume 的夾角 + 停留計時)。LLM 僅事後複核分類邊界案例與調整參數建議。

### A2. 百萬 Token 上下文的成本誤用
- 問題：藍圖建議「單次推理請求中載入個案數週甚至數月的完整紀錄」。以每週數萬筆 DTT 試驗計，每次覆盤都接近填滿上下文窗口，成本與延遲不可控，且長上下文中間段的檢索品質會下降。
- 修訂：改為階層式摘要 (session → week → month 三級滾動摘要) + 檢索式載入 (只取與本次分析目標相關的原始片段)。原始 60Hz 軌跡在邊緣端先降維為特徵 (首次注視延遲、轉移次數、停留分佈)，雲端只收特徵。

### A3. 安全拒絕自動改道至他模型 (定位錯誤)
- 問題：藍圖 6.2 將 Fable 5 的安全分類器拒絕視為單純技術故障，設計成「自動無縫重定向至 Opus 4.8」。把「被安全機制攔截的同一請求原封不動送給防護較少的模型」本質上是規避安全機制，可能違反供應商使用政策，也會在審計時構成重大缺陷。
- 修訂：區分兩類失敗。(1) 可用性失敗 (逾時、5xx、限流)：允許自動備援至同級模型。(2) 安全拒絕：不自動改道；請求進入隔離佇列，記錄、脫敏、由工程與臨床雙人覆核後決定重構提示詞或人工處理。同時在提示詞工程階段就避免夾帶原始程式碼片段與可疑模式，從源頭降低誤觸發。

### A4. 資料傳輸格式過重
- 問題：`eye_gaze_trajectory` 以 JSON 向量陣列序列化 60Hz 資料，單場 30 分鐘會話約 10 萬筆向量，JSON 膨脹嚴重。
- 修訂：邊緣端以 Protocol Buffers / Apache Arrow 儲存原始軌跡 (僅本地保留)，上傳僅含統計特徵。Schema 草案見 `schemas/`。

### A5. 單一供應商鎖定與模型生命週期
- 問題：全系統臨床邏輯與單一供應商的特定模型版本深度耦合；藍圖自己也引用了該模型曾因外部因素暫停服務的報導，卻未設計對應的架構解耦。
- 修訂：閘道層定義供應商中立的「臨床推理介面」(能力描述 + 結構化輸出契約)，模型名稱全部走設定檔；每季執行替代模型回歸測試集，確保可在 30 天內切換供應商而不影響療程。

## B. 事實性與引用品質問題

### B1. 關鍵事實依賴二手部落格與新聞聚合站
- 問題：定價 (每百萬輸入 10 美元 / 輸出 50 美元)、三十天資料保留且無零保留豁免、「99% 觸發攔截與誤報」、出口管制停機等關鍵敘述，引用來源多為第三方部落格 (Truefoundry、AY Automate、Substack、Financial Express 等)。其中「99% 誤報率」在工程上不可信 (若為真該模型等於不可用)，極可能是以訛傳訛。
- 修訂：所有涉及模型定價、資料保留、合規條款的敘述，一律以 Anthropic 官方文件 (platform.claude.com / anthropic.com 與正式合約條款) 為唯一依據，並在設計文件中標注查證日期。預算模型與合規設計不得建立在未經查證的數字上。

### B2. 模型名稱與版本混用
- 問題：藍圖同時出現「Sonnet 5」與「Haiku 4.5」「Opus 4.8」，型號名稱未經查證，可能與實際產品線不符。
- 修訂：文件中僅以能力層級代稱 (fast-tier / balanced-tier / deep-tier)，實際模型字串集中於 `gateway/models.yaml` 設定檔，由工程團隊對照官方模型列表維護。

## C. 臨床與倫理問題

### C1. 頭戴式 AR 與感官敏感的矛盾
- 問題：藍圖以「VR 頭顯對觸覺防禦個案極度困難」為由選擇 AR，但主要載具仍是「AR 穿戴裝置」，同樣需要頭戴。此為自我矛盾。
- 修訂：Phase 0-2 以平板 / 桌面固定式 AR (手機或平板鏡頭 + 螢幕疊加) 為主要載具；頭戴式僅在 Phase 3 作為選配，且引入前需完成個案感官耐受性評估與漸進式適應計畫。

### C2. 增強特效的感官超載與光敏風險
- 問題：「真實房間內綻放虛擬煙火」等頂級增強特效，對感官處理異常個案可能造成超載，高頻閃爍亦有光敏性癲癇風險。
- 修訂：所有視覺特效受硬性約束：閃爍頻率 ≤ 3Hz (參照 WCAG 2.3.1)、亮度與音量上限、單次特效時長上限。每位個案建立「感官設定檔」(由照護者與 OT/BCBA 填寫)，特效庫依設定檔過濾。預設特效一律為低刺激版本。

### C3. 休息卡 (FCT) 可能過度增強逃避
- 問題：系統在偵測到焦躁前兆時「主動」彈出休息卡，若門檻設定不當，等於教會個案「輕微躁動即可移除任務」，反而強化逃避行為。
- 修訂：休息卡的出現條件、每會話可用次數、排程稀釋曲線，全部列為 BCBA 授權參數，系統只提供建議值不得自動調整。同時記錄每次休息卡使用的完整 ABC 脈絡供功能行為評估 (FBA) 覆核。

### C4. 「焦躁前兆偵測」的偽陽性風險
- 問題：以姿態與聲學推斷情緒狀態，對 ASD 個案 (常有刻板動作與非典型發聲) 偽陽性極高，錯誤介入本身就是干擾。
- 修訂：前兆偵測模型必須以個案自身基線做個別化校準 (per-child baseline)，冷啟動期僅記錄不介入；介入決策需連續多信號共同觸發，且照護者可一鍵標注誤判以持續修正。

### C5. IEP 的法律屬性
- 問題：藍圖稱 Fable 5「動態生成 IEP」。在美國法規 (IDEA) 下 IEP 是由 IEP 團隊 (含家長) 制定的法律文件，AI 不能是作者。
- 修訂：系統輸出物正名為「IEP 目標建議草案 / 數據摘要報告」，僅作為 IEP 會議的參考輸入。介面與文件不得出現「AI 生成 IEP」的表述。

### C6. Assent 與中止權
- 問題：藍圖未定義個案本人的退出機制。
- 修訂：每個會話介面常駐「停止」手勢與圖卡；連續拒絕、負向情緒指標達門檻時系統自動結束會話並通知照護者。此為神經多樣性原則的落地要求，不可省略。

## D. 隱私與合規問題

### D1. 去識別化 ≠ 合規完成
- 問題：藍圖假設「本地去識別化」即可因應三十天資料保留。醫療情境下 (美國) 仍需 BAA 商業夥伴協議、兒童資料需 COPPA 可驗證家長同意、學區部署涉及 FERPA；眼動與聲學特徵在多州法律下屬生物特徵資料 (如 Illinois BIPA)。影像模糊化對重識別攻擊並非萬無一失。
- 修訂：(1) 原始影像與音訊一律不出裝置，雲端僅收結構化衍生特徵，從資料類型上根本降低風險面。(2) 與供應商簽署 BAA / 企業級資料處理協議，並向官方確認實際可用的資料保留選項，而非依據部落格轉述。(3) 建立同意管理模組：家長同意、學區協議、個案 assent 三層。(4) 聘請醫療隱私法遵顧問做上線前審計；若後續納入成效研究則送 IRB。

### D2. 資料主權與跨境
- 修訂補充：部署區域選擇需支援資料駐留要求 (data residency)；台灣或其他地區部署需另行對照當地個資法 (如 PDPA)。

## E. 缺漏補充 (原藍圖未涵蓋)

1. 離線模式：治療室網路不可靠，L1 必須可完全離線執行整場會話，事後同步。
2. 照護者端 App：家庭類化 (generalization) 是 ABA 成效關鍵，需提供家長端簡化任務與數據回報。
3. 成效驗證計畫：採單一受試者實驗設計 (multiple baseline across skills)，預先註冊分析計畫，避免只有產品沒有證據。
4. 事故應變：定義「系統誤增強危險行為」「特效引發情緒崩潰」等臨床事故的通報與回滾 SOP。
5. 無障礙：介面本身需符合 WCAG 2.2 AA，支援 AAC 相容輸入。
